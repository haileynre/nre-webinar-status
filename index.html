Fixing 232b under lead surges (drafts)

⚠Why it breaks

The error comes from n8n's own internal database, not from a Postgres node in the workflow. Three things combine during a surge:

Tiny connection pool. DB_POSTGRESDB_POOL_SIZE is never set, so each n8n container gets the default of 2 connections, while each worker runs up to 10 executions at once.

One lead becomes many saved runs. 232b → ledger tap (923x) → 323a → about 11 sub-workflows. Each one writes a run record to the database.

Background load. 235w. Write Bus Drain runs every 2 seconds, about 43,000 runs a day, and each one uses the same database.

When connections run out, the webhook itself can fail. AC hasn't disabled the webhooks (confirmed active Sep 28), but repeated failures put that at risk. (n8n also returned a 502 "origin overloaded" once while this review was running.)

Nothing below has been applied. Each fix needs Matt's approval. Suggested order: A and B first (quick, lowest risk), then C, then D.

Infra · n8n container config → local.n8n_env · applies to main and workers

D · Queue registrants instead of processing them live

n8n · 232b + new 323f. Registrant Queue Drain (draft in HAILEY folder) · marketing database

This is the fix for surges we can't control. 232b only saves the registrant to a queue table and returns straight away. A drainer pulls 20 every 30 seconds (about 2,400 an hour) and calls 323a one at a time. A surge makes the queue longer instead of causing failures, AC always gets a fast success reply, and every registrant has a row to audit.

AC tag webhook→ 232b · insert row→ registrant_queue→ 323f · 20 per 30 s→ 323a hub

It's a separate table because 235w claims every row in write_queue regardless of action, so it would pick up registrant rows and mark them unknown.

1 · New table 
CREATE TABLE IF NOT EXISTS registrant_queue (LIKE write_queue INCLUDING ALL);
-- same columns, unique event_id, defaults. Note: shares write_queue's id sequence.

3 · New workflow 323f. Registrant Queue Drain 
every_30s [schedule]
  → claim [postgres]
  → Loop Over Items (batch 1)
      → register [executeWorkflow 323a, waitForSubWorkflow: true,
                  onError: continueErrorOutput]
          ok  → mark_done  → execution_data (name, phone, email)
          err → mark_retry → execution_data (name, phone, email)
settings: executionTimeout 600, errorWorkflow shared-error-handler,
          saveDataSuccessExecution none
-- claim: 20 rows, skips if a batch is still in flight
WITH inflight AS (
  SELECT count(*) AS n FROM registrant_queue
  WHERE status = 'working' AND updated_at > now() - interval '2 minutes'
), cand AS (
  SELECT id FROM registrant_queue
  WHERE attempts < 5
    AND (status = 'queued'
         OR (status = 'working' AND updated_at < now() - interval '10 minutes'))
    AND (not_before IS NULL OR not_before <= now())
    AND (SELECT n FROM inflight) = 0
  ORDER BY id
  LIMIT 20
  FOR UPDATE SKIP LOCKED
)
UPDATE registrant_queue q SET status = 'working', updated_at = now()
FROM cand WHERE q.id = cand.id
RETURNING q.id, q.event_id, q.payload, q.attempts;

-- mark_done
UPDATE registrant_queue
SET status = 'done', finished_at = now(), updated_at = now()
WHERE id = $1;

-- mark_retry: exponential backoff, gives up after 5 attempts
UPDATE registrant_queue
SET attempts   = attempts + 1,
    status     = CASE WHEN attempts + 1 >= 5 THEN 'failed' ELSE 'queued' END,
    last_error = left($2, 500),
    not_before = now() + (power(2, least(attempts + 1, 5)) || ' seconds')::interval,
    updated_at = now()
WHERE id = $1;

Tuning: raise LIMIT or shorten the interval for faster throughput. A stuck row is retried after 10 minutes. Rollback: re-enable the old Register node in 232b and disable enqueue_registrant. Any queued rows can be drained later.
